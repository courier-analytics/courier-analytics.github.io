# Импорт выгрузки смен

## Ручная история и начало инструмента

Ранее вручную введённые значения, включая нули, имеют приоритет и в интерфейсе,
и при заполнении истории. У 7745 за 18–22 октября сохранены ручные 0% второй
метрики. Даты начала инструмента: 5818 — 23 октября, 7745 — 25 октября.
Автоматические отношения участников расписания к пятидневной базе до этих
дат не подтверждают проставление смен в МП и не публикуются как эта метрика.
Старые импортированные 70,18% и 66,04% у 7745 за 23–24 октября исключаются;
без подтверждённого прежнего источника отображается прочерк.

## Дарксторы и новая точка 8092

Текущий список: 5818, 7745, 4747, 8092. `dashboard_shops.py` задаёт страницы
и начало их истории; у 8092 — 26.10.2026. `8092.html` содержит все десять
метрик и изначально только отсутствующие значения. Она доступна из выбора
ДС на каждой странице. Каталог автоматически определяет кластеры новой точки.
При отсутствии точки или прав API сбор не создаёт фиктивных нулей и продолжает
обрабатывать доступные точки. Основной сборщик, активная база, ночные смены,
фиксация плана, заполнение пропусков и валидатор публикации поддерживают 8092.

Для применения в существующем VPS-клоне обновляется рабочая ветка и запускается
`bash tools/backfill_missing.sh`; текущие таймеры переустанавливать не нужно.
Само наличие страницы не означает успешной проверки реального API новой точки.
Ручные метрики 1, 8, 9 и 10 не копируются из других ДС.

## Независимый сетевой доступ: текущий установщик

Для возврата к прежней схеме запускается обратный SSH-туннель с Мака
`-R 127.0.0.1:18080:127.0.0.1:10808`, затем на VPS выполняется
`bash tools/use_mac_proxy.sh`. Скрипт проверяет действующую сессию через 18080,
сохраняет маршрут для ручных команд и служб, запускает обновление и показывает
результат. Правила метрик и исторические значения не меняются. Мак, Happ и
окно туннеля должны оставаться включёнными. Серверный прокси не удаляется.

Если серверный порт 18081 открыт, но API через выбранный узел отвечает таймаутом,
`bash tools/repair_server_proxy.sh` скрыто запрашивает подписку ещё раз и
проверяет узлы по порядку на отдельном порту 18082. Рабочий узел должен достичь
API с HTTP 200 или 401 без авторизации. Затем проверяется действующая сессия,
публикуется пробная выгрузка и переключается планировщик. До нахождения
кандидата активный прокси и маршрут не меняются. Все проверки TLS сохранены.
Если ни один узел не работает, скрипт останавливается без выбора случайного
узла. Приватные ссылки и адреса узлов не выводятся.

`bash tools/setup_independent_access.sh` запускается **на VPS в SSH с `-t`**.
Он скрыто принимает стандартную VLESS-ссылку, HTTPS-подписку (VLESS-список или
base64) либо JSON одного узла. Секреты не печатаются и не передаются в аргументах
процессов. Файл узла сохраняется в `/root/courier-private-node.json` с правами
600. У подписки с несколькими узлами выбирается номер; ссылки Happ с
нестандартным шифрованием не поддерживаются, нужен стандартный экспорт провайдера.

Прокси Xray слушает только `127.0.0.1:18081`, самостоятельно запускается через
systemd и перезапускается после ошибки. Перед переключением проверяются все
три ДС и их кластеры существующей сессией; используются подтверждённый официальный
бинарник, проверка SHA-256 и включённая проверка TLS. Основные маршруты и рабочий
Mac-туннель не меняются. Старый сборщик не переустанавливается поверх настроенного
сборщика всех ДС. Сервисы сбора и фиксации плана получают зависимость от прокси.
Затем выполняется пробное обновление. Только после успешного завершения можно
проверять независимость, закрыв прежний туннель и запустив обновление ещё раз.

Все ручные команды теперь также читают `/etc/courier-analytics/proxy.env`;
явная переменная `COURIER_PROXY_URL` имеет приоритет. Этот файл не выполняется
как shell-код. При отсутствии настройки остаётся прежний маршрут 18080.

После установки `independent_readiness.py` печатает только признаки наличия
основной сессии/refresh-credential и результаты анонимного доступа к внутреннему
`izb-dwh-ssrs01/reports/` и каталогу Power BI Report Server. Содержимое отчётов,
пароли и токены не выводятся. Для этого внутреннего источника может понадобиться
отдельный корпоративный VPN/DNS и NTLM/Negotiate, даже когда публичный API смен
доступен через серверный VLESS. HTTP-пробы анонимны, HTTPS-проверка не отключается.

Это завершает перенос сетевого доступа, но **не подтверждает автоматическое
продление основной сессии и не подключает 10-ю метрику**. В изученном клиенте
основной вход — телефон/пуш-код; Firebase refresh относится к другой сессии.
Если нет документированного refresh или служебной учётки, бесконечный вход
без участия человека обещать нельзя. API/авторизация и поля внутреннего отчёта
ЛМК должны быть проверены до автоматической публикации медицинской метрики.

### Проверка внутреннего отчёта ЛМК через корпоративный VPN

`probe_powerbi_vpn.py --address CORPORATE_IPV4` запускается только на VPS под
root. Вместо `CORPORATE_IPV4` нужен фактический адрес `izb-dwh-ssrs01`, полученный
в корпоративной сети; адреса публичного API смен здесь не подходят. Используются
уже сохранённые `/root/courier-openvpn-tcp.ovpn` и `/root/courier-openvpn.auth`.
Другой работающий OpenVPN останавливать автоматически скрипт не будет.
В запросах используется подтверждённое через корпоративный DNS полное имя
`izb-dwh-ssrs01.izbenka.local`; HTTP Host и HTTPS SNI сохраняют это имя.

Проверка временно запускает корпоративный VPN с единственным маршрутом `/32`
к указанному серверу. Она не меняет системный DNS, основной маршрут, публичный
Xray-прокси, задания сбора или данные дашборда. До четырёх анонимных запросов
проверяют портал, отчёт ЛМК, каталог REST и HTTPS. Содержимое ответов удаляется;
печатаются только коды HTTP/curl и названия схем авторизации. Заголовки с
токенами остаются в закрытом временном файле, который удаляется после запроса.
Пароль для Power BI не передаётся, перенаправления не выполняются, проверка
TLS сохраняется. Временный VPN останавливается по завершении проверки.

Ответ HTTP 401 подтверждает сетевой доступ и необходимость авторизации, но не
доступ к данным. Даже HTTP 200 сам по себе не подтверждает правильность метрики.
Перед автоматизацией нужно проверить авторизованную выгрузку, поля ДС/даты,
правила действительности ЛМК и знаменатель процента. Эта диагностическая команда
не подключает метрику №10 и не восстанавливает исторические значения из текущего
состояния отчёта.

Для проверки авторизованного доступа добавлен `--save-login`: до запуска VPN
он проверяет наличие `/root/courier-powerbi.json`. Существующий закрытый файл
сохраняется; при его отсутствии логин Windows в формате `DOMAIN\user` или UPN
и пароль вводятся через `getpass`. Секреты сохраняются атомарно с правами 600.
Для явного исправления сохранённого входа нужны оба флага `--save-login
--replace-login`. Для последующих проверок без запроса ввода — `--check-login`.

Проверка использует исходный HTTP-сервис внутри корпоративного VPN и NTLM,
передаёт учётные данные curl через stdin, отключает пользовательский curlrc
и не следует перенаправлениям. Пароль не попадает в аргументы процессов,
переменные среды, вывод или Git. Запрашиваются только метаданные каталога с
фильтром на точный путь отчёта ЛМК. Ответ с неверным путём, несколькими
совпадениями или невалидным ID не считается успехом. Во временном закрытом файле
ответ ограничен 2 МиБ и удаляется; ID, путь и название нужного отчёта сохраняются
приватно для следующего этапа проверки выгрузки. Это не выгружает строки курьеров
и не включает автоматическую публикацию медицинского процента. Ошибку доверия
сертификату HTTPS нужно исправлять корпоративным CA, а не отключением проверки.
Перед авторизованным запросом дополнительно проверяется маршрут к серверу:
он должен идти через интерфейс `tunN`. curl привязывается к этому интерфейсу;
при исчезновении VPN учётные данные не отправляются через основной интерфейс.

После подтверждённого входа флаг `--inspect-model` повторно использует сохранённую
учётную запись и читает определение отчёта через GET `modelsAndExploration`
веб-клиента Power BI. Проверяются два варианта базового пути приложения;
неподдерживаемый путь не считается успешной проверкой. Это отдельный внутренний
API веб-клиента, а не документированный экспорт строк через REST-каталог:
совместимость с фактической версией сервера должна быть подтверждена ответом.
Запросы данных, изменение отчёта и публикация процентов не выполняются.
Определение до 8 МиБ сохраняется только приватно. В вывод попадают ограниченные
списки имён сущностей, полей, ссылок проекций и типов визуализаций; значения
фильтров и строки курьеров не печатаются. При неполном разборе ставится
`truncated: true`. Доверять полям и формуле метрики до просмотра реального ответа
нельзя. Максимальное время временного VPN увеличено до 240 секунд для чтения
метаданных; профиль и маршруты очищаются по завершении.

`python3 tools/powerbi_blueprint.py` работает локально на VPS с уже сохранённым
определением, без VPN и сетевых запросов. Он создаёт приватный
`/opt/courier-analytics/private/powerbi-query-blueprint.json`: идентификаторы
моделей, структуру запросов визуализаций ЛМК и привязки к `name_TT`. Значения
литералов фильтров, токены, пароли, строки данных, неизвестные поля запроса и
значения подключения не экспортируются. Сохранённые структуры с удалёнными
литералами нельзя выполнять как запрос; для адаптера на VPS используется исходное
приватное определение. Файл служит для проверки реальных полей, привязок и
формата запросов перед реализацией расчёта доли действующих ЛМК.

`probe_powerbi_vpn.py --address CORPORATE_IPV4 --collect-medical` проверяет
реальную выгрузку агрегатов без публикации. `--shops` ограничивает результат
ДС 5818/7745 (по умолчанию обе). Учётная запись повторно используется, а
определение отчёта и runtime model ID обновляются перед каждым запросом.
На основании проверенной структуры таблицы формируется read-only POST
`/powerbi/api/explore/reports/{report_id}/querydata`: только `main_mc06.name_TT`, «Всего курьеров»,
«Курьеров с ЛМК», «Курьеров, ЛМК просрочена» и процент без ЛМК либо с просрочкой.
ФИО, ID курьеров и индивидуальные медицинские даты в Select не включаются.
Фактический формат ответа этой версии сервера должен быть подтверждён запуском;
успешные локальные тесты не подтверждают работу RPC на сервере.
ID берётся из подтверждённого каталога отчёта, проверяется как UUID и входит в
путь запроса данных, как и при чтении определения. При ошибке выводятся только
безопасный код, имена полей валидации и категории, без текста серверных сообщений.

Процент действующих ЛМК считается как `(с ЛМК - просрочено) / всего * 100`.
Он принимается только при согласованности с дополнительным показателем
«% курьеров нет ЛМК или просроченные» из того же контекста. Пустые значения не
становятся нулями. Неверные счётчики, неоднозначные названия ДС, неизвестное
отображение колонок DSR, пагинация и достижение окна 5000 строк блокируют
кандидат. Поддерживаемый плоский DSR разбирается с учётом словарей, повторов,
null-масок и дескриптора колонок. Карточки полей в панели фильтров без `Where`
не считаются активными условиями. Активные условия формата ТТ и `name_TT`
сохраняются с корректным сопоставлением алиасов источника. Условия на отдельных
курьеров, медицинский статус и агрегатные меры блокируют расчёт, чтобы не
изменить знаменатель покрытия. Неизвестные формы фильтров не игнорируются.
При отсутствии необязательного скомпилированного запроса используется
`prototypeQuery` самой таблицы или матрицы, с теми же проверенными полями.
Диагностика выбора таблицы не выводит значения фильтров.
Неиспользуемые объявления таблиц в `From` фильтра не добавляются в запрос
и не блокируют его. Сервер подтвердил, что таблица `customer_complaint`
отсутствует. Для отдельного расчёта действующих ЛМК условие, ссылающееся
только на `customer_complaint.tag`, исключается с отметкой в диагностике.
Смешанные условия с другими полями блокируют сбор; остальные фильтры
сохраняются. Неизвестные таблицы не заменяются автоматически.
`--collect-medical --preflight` сначала проверяет уже сохранённое определение
локально. Если его структура не поддерживается, печатаются только сущности
и имена полей активных условий; VPN и сетевые запросы не запускаются.
Это флаг для ручной диагностики сохранённой структуры, а не проверка свежести
источника: обычный сбор по-прежнему перечитывает определение на сервере.

Сырой ответ сохраняется только в приватном `powerbi-medical-query-response.json`;
при успешной проверке создаётся приватный `medical-books-candidate.json`.
В выводе — только агрегаты выбранных ДС и техническая структура ответа.
Дата кандидата — день наблюдения в Москве; текущее состояние Power BI не
подменяет исторические медицинские показатели. Время чтения не выдаётся за
время обновления модели источника. Эта команда не устанавливает таймер и не
меняет публичный дашборд: публикация подключается после проверки реальных чисел.

`import_slots.py` читает лист «Смены» XLSX, создаваемого кнопкой
«Выгрузить слоты». Требуется Python 3 и `openpyxl`:

```sh
python3 -m pip install openpyxl
python3 tools/import_slots.py /путь/к/отчёту.xlsx
python3 -m unittest discover -s tests -v
```

Команда выводит только агрегаты. Исходные выгрузки, сессии и токены нельзя
класть в репозиторий или каталог публичного сайта. При вызове `read_export`
из Python результат содержит ID курьеров; он предназначен для защищённой
обработки на сервере, не для публикации.

Обработка:

- Одна строка XLSX — слот; список ID курьеров разбирается отдельно.
- Охват берётся из самого отчёта: учитываются и прямые слоты ДС,
  и включённые в выгрузку кластеры. Один `shopno` не заменяет этот охват.
- Групповым строкам не присваиваются общие статус и время смены:
  каждый курьер получает признак `api_required`.
- Пустое окончание смены означает неизвестное значение, а не завершение
  или невыход. Классификация посещаемости пока не реализована.
- Заполненность мест = сумма «Записалось» / сумма вместимости.
  Уникальные курьеры считаются отдельно; одинаковый человек в двух слотах
  занимает два места. При нулевой вместимости процент равен `null`.
- Повторные слоты и несовпадение количества ID с записавшимися приводят
  к ошибке вместо публикации неполных итогов.

Проверенный образец за 25.10.2026: ДС 5818, 42 лимитированных слота,
102 места, 57 записей курьер–слот, 56 уникальных курьеров, 14 групповых
слотов. 48 записей требуют индивидуальной детализации из API.
Это 55,88% занятых мест. Скриншот показывал 56/102: снимки ещё нужно
сопоставить по времени и логике подсчёта; не подменять 57 мест 56 людьми.

## Дополнение через API

`enrich_slots.py` получает детали по каждому дню, типу слотов и каждой
области выгрузки: прямой ДС и всем указанным кластерам. Читает существующий
файл сессии; токен передаётся curl через stdin, не через аргументы процесса.
Проверка TLS включена. Запросы только GET, изменение слотов не выполняется.

```sh
python3 tools/enrich_slots.py /защищённый/путь/report.xlsx \
  --session /root/curator-session.json \
  --proxy socks5h://127.0.0.1:18080 \
  --output /opt/courier-analytics/data/enriched-summary.json
```

Объединение идёт по дате, типу, ID слота, ID курьера и области запроса.
Повторные ID отклоняются. Изменения состава записавшихся, вместимости,
времени и отсутствие слота дают диагностику и код выхода 2; предыдущий
отчёт остаётся нетронутым. Новые слоты из API не добавляются в старый Excel.
Индивидуальные статусы, время записи, начало и конец сохраняются отдельно
в памяти. На диск выводятся только агрегаты и диагностика, без имён,
телефонов и ID курьеров. Отсутствующие факты не восстанавливаются догадками.

`attendance_metrics_ready` пока всегда `false`: показатели выхода,
опозданий и завершения смены не публикуются до проверки правил и снимка
плана. XLSX не содержит время записи, необходимое для фиксации плана на
23:59; оно запрашивается в API. Историю плана нельзя восстановить полностью
из текущих записей, если записи уже удалены.

Реальное чтение XLSX и живое API-обогащение проверены на VPS: 57 записей,
14 групповых слотов, пять записей без времени окончания, расхождений нет.
Локальный SOCKS-прокси пока зависит от Mac/Happ/SSH-туннеля.

## Регулярное обновление и сайт

`build_dashboard_feed.py` публикует только дату, ДС, числитель, знаменатель,
процент и время отчёта. Пример для уже проверенного отчёта:

```sh
python3 tools/build_dashboard_feed.py /opt/courier-analytics/data/enriched-summary.json \
  --output /opt/courier-analytics/site/data/dashboard.json
```

Страницы читают `data/dashboard.json` при открытии, по кнопке и раз в минуту.
Новые даты добавляются к истории. Заполняется только строка заполнения слотов;
остальные новые метрики остаются `null`. При ошибке загрузки последнее
успешное состояние сохраняется. CSV отражает загруженную таблицу.
Наличие файла не подтверждает работу планировщика или свежесть API:
на странице показывается время исходного отчёта.

`refresh_dashboard.py` позволяет не загружать Excel вручную: читает API,
создаёт собственный защищённый XLSX на основе тех же полей, затем формирует
отчёт и публичный JSON. Это программный экспорт данных, а не нажатие кнопки
в браузере и не побайтовая копия файла сайта. При ошибке предыдущий
публичный файл не изменяется. Даты истории сохраняются.

```sh
python3 tools/refresh_dashboard.py --scopes tools/scopes.json \
  --feed /opt/courier-analytics/current-site/data/dashboard.json
```

В `scopes.json` пока только проверенный по XLSX охват ДС 5818. ДС 7745 не
добавлена: её кластеры ещё не установлены. Если меняется состав кластеров,
конфигурацию необходимо актуализировать; файл не обнаруживает их автоматически.
При расчёте нового дня снимок всех API-запросов не транзакционный:
изменения между запросами возможны. Новые XLSX хранятся в закрытом каталоге.

`deploy_dashboard_from_mac.sh` переносит версию в отдельный каталог VPS,
выполняет живое обновление и только после успеха меняет `current-app` и
`current-site`. На GitHub ничего не публикует. При обновлении сохраняет
предыдущую историю из текущего файла данных. Требуются работающие Happ,
SSH-туннель, файл сессии и Python venv на VPS.

Подготовлены `courier-refresh.service` и `.timer` с блокировкой `flock`.
Они обновляют текущий день каждые 15 минут; завершающий пересчёт предыдущего
дня отдельно ещё не реализован. Установка и включение таймера не выполнялись.
Пока прокси зависит от Mac, расписание нельзя называть автономным.
Статический GitHub Pages не видит файлы VPS: для публикации нужны отдельная
выкладка JSON в репозиторий либо перенос размещения сайта на VPS.

## Публикация данных в GitHub Pages

`publish_dashboard.py` проверяет публичный JSON и отправляет только
`data/dashboard.json` в `main` отдельным SSH deploy key. Вспомогательный
клон принадлежит этому инструменту; при посторонних локальных изменениях
публикация останавливается. Перед каждым обновлением загружается свежий
`main`, изменения HTML не затрагиваются. История удалённых дат сохраняется.
Force push не используется: конкурентное обновление отклоняет push,
следующий запуск повторяет публикацию от свежего состояния.

`setup_publisher.sh` запускается на VPS, создаёт отдельный ключ, получает
SSH host keys GitHub с официального HTTPS API и устанавливает systemd units.
В выводе только публичный ключ; приватный файл остаётся на сервере с правами
600. Публичный ключ требуется добавить в Settings → Deploy keys этого
репозитория с разрешением записи. Такая запись разрешает Git push в
репозиторий; программно инструмент ограничен файлом агрегатов. Защита ветки
может блокировать push: в таком случае ничего не форсировать, а настроить
согласованный способ публикации отдельно.

После добавления deploy key выполнить `systemctl start courier-refresh.service`
и проверить результат, затем `systemctl enable --now courier-refresh.timer`.
Таймер устанавливается, но скрипт настройки сам его не включает. Логи:
`journalctl -u courier-refresh.service -n 30 --no-pager`.
Публикация коммита не доказывает завершение сборки Pages — проверить HTTP
ответ сайта и JSON. Пока Happ/SSH-прокси зависит от Mac, полная автономность
не достигнута. Ключ публикации этот сетевой вопрос не решает.

Установка из клона репозитория на VPS: `bash tools/install_on_vps.sh`.
Скрипт использует существующую сессию и SOCKS-прокси, проверяет живой запрос,
создаёт отдельный каталог сайта и только после успеха меняет ссылки
`current-app` / `current-site`. История активного JSON сохраняется.
Сам сайт GitHub Pages и расписание при этом не изменяются.

## Серверный прокси без Mac

`install_server_proxy.sh /root/private-node.json` запускается на VPS после
экспорта одного рабочего VLESS-узла из Happ в Xray JSON. Подписка целиком,
несколько VLESS outbounds и цепочки прокси не поддерживаются. Не передавать
этот файл в чат, Git, каталог сайта или публичные артефакты. Файл содержит
учётные данные подключения. Сначала убедиться, что подписка допускает
подключение с другого устройства; это не проверяется программой.

`prepare_proxy_config.py` сохраняет параметры выбранного узла и создаёт
единственный SOCKS inbound на 127.0.0.1:18081. Маршрутизация, DNS, входящие
порты и привязки интерфейсов из конфигурации Mac не копируются. Настройки
с отключённой проверкой TLS отклоняются. Для Reality сохраняются имя
сервера и публичный ключ; серверный privateKey отклоняется.

`download_xray.py` скачивает официальный Xray-core v26.10.21 для Linux x86_64.
Артефакт проверяется SHA-256 из официального GitHub Release API до распаковки.
Проверка TLS включена. Версия и checksum зафиксированы в исходном коде.
Из архива извлекается только бинарный файл; произвольные пути не распаковываются.

Установщик сначала проверяет конфигурацию через `xray run -test`, затем
поднимает непривилегированную службу `courier-proxy`. Перед переключением
таймера выполняются запрос без токена и авторизованное получение агрегатов
через новый прокси. Если эти проверки не проходят, прежние файлы службы
прокси восстанавливаются, SSH-туннель на 18080 остаётся без изменений.
Ошибки ядра сохраняются в закрытом каталоге /root; полный лог не отправлять
в чат без проверки на конфиденциальные значения.

После успеха `/etc/courier-analytics/proxy.env` задаёт
`COURIER_PROXY_URL=socks5h://127.0.0.1:18081`; unit обновления читает этот
файл. Служба прокси запускается после загрузки ОС и перезапускается при сбое.
Не меняются default route, firewall или настройки корпоративного OpenVPN.
После установки обязательно выполнить один цикл обновления и публикации
с закрытым Mac SSH-туннелем. Только успешная проверка после отключения Mac
позволяет заявить, что эта зависимость устранена.

Пока проверены: unit-тесты преобразования и защиты конфигурации,
официальный checksum скачанного бинарного файла и `Configuration OK`
на тестовой конфигурации. Реальное подключение с профилем пользователя
и работа systemd-прокси на VPS ещё не проверены.

## Охват всех ДС и плановые показатели

`discover_scopes.py` повторяет AF/PF/LF из проверенного клиентского кода:
числовые идентификаторы ДС в названиях кластеров и cluster_id из карточки
точки. Это тот же алгоритм выбора, который использует сайт, а не подбор
кластеров по близким ID. Цели: 5818, 7745, 4747. Отсутствующая точка или
HTTP 403/404 для её слотов не превращается в нулевой показатель.

`audit_sources.py` одной командой получает каталоги, ручные и лимитированные
слоты всех доступных точек, проверяет схемы списка курьеров и истории
записей. В stdout только агрегаты и типы полей. Имена и телефоны из ответов
не сохраняются; ID курьеров и времена сохраняются в закрытом каталоге для
сопоставления. Команда сама не меняет таймер или сайт.

`calculate_metrics.py` считает людей уникально: несколько слотов одного
курьера не увеличивают знаменатель числа курьеров. Заполнение считает
места, отдельно. Показатель отметок смены требует подтверждённого полного
списка закреплённых курьеров. Пока семантика ответа roster не проверена,
показатель получает `assigned_roster_not_verified`, а не выдуманный знаменатель.

Выход по плану, опоздания и внеплановые выходы требуют реального снимка
плана накануне. Текущее время записи не доказывает полный исторический
состав: удалённые записи могли исчезнуть. При отсутствии снимка возвращается
`frozen_plan_missing`. При исчезнувших плановых записях или изменении времени
слота расчёт не проводится до проверки истории. Опоздавшим считается
уникальный курьер с хотя бы одним плановым статусом «Опоздал», знаменатель —
уникальные вышедшие по плану. Внеплановые — вышедшие в ручных слотах без
курьера в зафиксированном плане, знаменатель — все фактически вышедшие.

Завершение смены оценивается по фактическому окончанию всех плановых слотов
курьера, с допуском 10 минут из BM/zM исходного сайта. Знаменатель — все
уникальные плановые курьеры. Отсутствие окончания/окончательного статуса
сохраняется как неизвестность; не трактуется как выполненная смена или 0%.
Проценты текущего дня являются состоянием на время выгрузки.

`capture_plan.py` фиксирует следующий день только в минуту 23:59 МСК.
Если сбор вышел за границу минуты, снимок не признаётся корректным.
`courier-plan.timer` использует явный часовой пояс Europe/Moscow и не
воспроизводит пропущенную фиксацию задним числом. Снимок сохраняется атомарно,
с правами 600; существующий снимок не перезаписывается.

`refresh_all_shops.py` собирает полный доступный охват трёх ДС и публикует
только рассчитанные показатели и причины пропусков. Сохраняет закрытый
XLSX и наблюдения. `enable_all_shops.sh` сначала проверяет живые данные и
публикацию, затем переключает unit обновления и включает ночной таймер.
Существующий маршрут Happ/SSH не меняется. До живого запуска это проверено
только тестами и браузерными сценариями; результаты других ДС не выдумываются.

Данные JSON поддерживают необязательный `metrics` со строгим списком полей,
формулой числитель/знаменатель и кодом причины отсутствия. Публикуемые данные
не содержат ID, ФИО, телефонов и токенов. Все три страницы, включая 4747,
умеют показывать новые показатели и причины прочерков в подсказках.
# Проверка реестра закреплённых курьеров

## Заполнение пропусков истории

`bash tools/backfill_missing.sh --date 2026-10-26` повторно рассчитывает только
26 октября для всех настроенных ДС, включая уже рассчитанные автоматические
значения 2, 3, 4, 5 и 7. Вручную внесённые значения сохраняются; снимки плана
читаются из общей приватной папки. Без `--date` сохраняется режим заполнения
только отсутствующих значений.

`bash tools/backfill_missing.sh` заполняет отсутствующие показатели `slot_fill`,
`shift_marked`, `planned_attendance` и `planned_late` до текущего московского дня
включительно для всех трёх ДС.
Начало берётся из существующей истории каждой страницы: 08.10 для 5818,
18.10 для 7745 и 21.10 для 4747 (2026 год). Существующие ручные значения,
включая нули, сохраняются. Ответ «нет лимитированных мест» считается полным
ответом с прочерком, а не пропущенной датой. Предыдущий валидный импорт
заполнения также сохраняется при добавлении отсутствующей доли записавшихся.

Данные за прошлые дни — наблюдаемое сейчас историческое расписание с текущим
сопоставлением ДС и кластеров, а не снимок состояния на тот момент.
План накануне не восстанавливается из текущих записей; обучение,
медкнижки, обращения и прогноз без своего источника не заполняются.
Активная база для каждой даты считается отдельно за неё и четыре предыдущих
дня. Обработка держит существующую блокировку обновления, готовит приватный
кандидат и публикует только после проверки всех нужных дат. Ошибка оставляет
активный сайт прежним. Успешный повтор пропускает уже заполненные показатели.

Для 4-й и 5-й метрик пользователь уточнил источник: карточки лимитированных
слотов. При отсутствии сохранённого плана используется текущий список
записавшихся: 4-я = уникальные вышедшие / уникальные записавшиеся;
5-я = уникальные опоздавшие / уникальные вышедшие. Статусы «вышел», «раньше»
и «опоздал» подтверждают выход; «не вышел» и «ожидается» — нет.
Любой неизвестный статус оставляет обе метрики без значения. Курьер с несколькими
записями считается один раз; любое опоздание включает его в числитель 5-й метрики.
Ручные слоты в этот вариант не входят. Подсказка явно сообщает, что основание —
текущие карточки, а не доказанный план накануне; для текущего дня результат
промежуточный. Сохранённый план, когда доступен, остаётся приоритетным.
6-я метрика по-прежнему требует проверенного плана.

Для 7-й при отсутствии сохранённого плана также используются карточки
лимитированных слотов: уникальный записавшийся курьер считается завершившим
смену, если завершены все его слоты. Фактический уход сравнивается с окончанием
слота (для ночных — на следующую дату); допуск сайта — 10 минут.
Неявка означает незавершение, а отсутствующий/неразбираемый уход, время без
часового пояса или неизвестный статус оставляют показатель без значения.
Если хоть один занятый слот ещё не закончился, итог пока не рассчитывается.
Знаменатель — все уникальные записавшиеся в эти слоты, не число мест.
Это расчёт по текущим карточкам, не доказательство состава плана накануне.
Повторный `backfill_missing.sh` заполняет и пропуски 7-й метрики, сохраняя
ручную историю. Неполные факты окончания оставляют прочерк и не препятствуют
публикации остальных доступных значений.

Ночная смена без отметки ухода дополнительно проверяется в API за следующий
день, в том же ДС или кластере. Связь принимается только при совпадении ID
курьера и фактического начала смены с часовым поясом. Совпадение одного ID,
другая смена, несколько противоречивых окончаний или недоступный следующий
день не позволяют подставлять время. В приватном результате отмечается дата
источника дополнения. Вывод backfill содержит `Overnight end check` с количеством
восстановленных записей и причинами неудачного сопоставления.
Незаконченные и будущие ночные слоты не запрашиваются.

## Активная база по расписанию за пять дней

### Уточнение 7-й метрики: дата ночной смены

По указанию пользователя правило даты фактического завершения применяется
только к 7-й метрике. Для неё ночная смена относится к московской дате
фактического ухода, даже если он произошёл на несколько дней позже начала.
Открытая ночная смена ещё не имеет отчётной даты и не блокирует день начала;
неявка без фактического ухода также не попадает в список завершённых ночных
смен. Дневные слоты сохраняют дату слота, а все остальные метрики — прежние
правила дат. Допуск окончания 10 минут сохраняется.

`completion-night-state` приватно хранит исходные ночные слоты и перепроверяет
незакрытые. При первом запуске проверяются даты с дня перед началом истории
соответствующего ДС. Это может занять больше времени; последующие запуски
используют кеш закрытых смен. При неполном ответе источника 7-я метрика
остаётся без значения. Следующие дневные записи с теми же ID и фактическим
началом смены не заменяют исходное плановое время и не задваивают смену.
Ранее автоматически рассчитанная 7-я метрика со старым основанием будет
пересчитана командой `backfill_missing.sh`; вручную внесённая история сохраняется.

После сверки с фильтром сайта активная база берётся из `shopno` самого ДС:
у 5818 за 22–26.10.2026 это 87 ID; объединение с кластерами давало 99.
Это уникальные участники расписания, а не список закрепления и не подтверждение
фактического выхода. Период включает выбранную дату и четыре предыдущих дня,
ручные и лимитированные слоты. Числитель — уникальные участники расписания
на выбранный день в ДС и его кластерах, входящие в эту активную базу.
Курьеры, встречающиеся за пять дней только в кластерах, не увеличивают базу
или числитель.
Заполнение мест по-прежнему учитывает ДС и связанные кластеры отдельно.

`bash tools/enable_active_base.sh` проверяет свежие данные всех трёх ДС,
публикует только валидный кандидат и затем включает расчёт в существующем
обновлении. Каждый запуск заново проверяет четыре прошлых дня; неполные ответы
дают прочерк для этой метрики. Старые исторические метрики не пересчитываются.
Это заменяет прежний план использовать полный реестр 1С для знаменателя.

`python3 tools/audit_roster.py` проверяет реестр отдельно для 5818, 7745 и

### OpenVPN candidate preparation

Medical query responses can contain semantic errors inside HTTP 200 results.

references a missing entity. For the separately requested valid-LMK calculation, predicates referencing only

### Проверка и включение фиксации плана

```bash
bash /opt/courier-analytics/dashboard-code/tools/enable_plan_capture.sh
```

Команда показывает прежнее состояние таймера и последние записи службы,
устанавливает актуальный сборщик на 23:59 МСК и проверяет сохранённые планы
за вчера, сегодня и завтра. Вне установленного окна новый план не создаётся.
Для вчерашнего дня проверяется подлинное время начала/окончания снимка.
При наличии снимка собираются свежие фактические выходы, пересчитывается
только `unplanned_work` и публикуется результат с сохранением остальных метрик.
При отсутствии снимка выводится явная причина; процент не выдумывается.

Внеплановые — все уникальные фактически вышедшие, отсутствующие в сохранённом
плане, независимо от ручного или лимитированного типа слота. Знаменатель —
все фактически вышедшие уникальные курьеры ДС и его подтверждённых кластеров.
Перенос записи в другой слот не превращает планового курьера во внепланового.
Неизвестные статусы блокируют расчёт; ожидание и неявка выходами не считаются.
Исторический пересчёт принимает подтверждённое сравнение с планом вместо
ранее опубликованного отсутствующего показателя, сохраняя ручные значения.

`verify_plan_capture.sh` устанавливает обновлённую службу фиксации и запускает
отдельный `courier-plan-check.service` с теми же пользователем и proxy.env.
Проверка читает завтрашние слоты обеих ДС, но не создаёт замороженный план.
Результат проверки виден в журнале, включая отказ при сетевой ошибке.
Фиксация в 23:59 повторяет кратковременные ошибки соединения (включая curl 35)
до трёх попыток с паузой 2 секунды, только пока действует исходное окно.
Сбор, завершившийся после полуночи, всё равно отклоняется; окно не расширяется.

Опоздания учитываются начиная с 15 минут включительно. Если фактическое
время начала смены известно, сравниваются точные секунды с началом слота;
иначе используется длительность в статусе (часы/минуты/секунды).
Задержка 14:59 не входит в числитель, 15:00 входит. Знаменатель — все
фактически вышедшие уникальные курьеры; небольшое опоздание не исключает
курьера из знаменателя. При неизвестной длительности опоздания процент
не подменяется нулём: причина `lateness_duration_missing`. Правило действует
и при сравнении с замороженным планом, и при расчёте по текущим слотам.

### Проверка штатного браузерного входа в 1С

В полученном `mod_main_loader.js` подтверждены `userName`, `userPassword`,
`okButton`, обмен `additionalAuthSettings` → `e1cib/login` и конечное поле
`passwordExpirationStatus`. Самостоятельная подмена challenge-response не
используется: форму обслуживает исходный браузерный клиент 1С.

```bash
bash /opt/courier-analytics/dashboard-code/tools/setup_onec_browser.sh
/opt/courier-analytics/onec-venv/bin/python /opt/courier-analytics/dashboard-code/tools/probe_powerbi_vpn.py --address 10.210.254.19 --onec-login --onec-save-login
```

Runtime устанавливается отдельно в `onec-venv`; установка Chromium включает
его системные библиотеки. Существующий импортёр использует прежний venv.
Оба реквизита вводятся скрыто и сохраняются в `/root/courier-onec.json` (600).
Повторный запуск сохраняет существующие реквизиты. Пароли не передаются в
URL, аргументах, переменных окружения или диагностике. Ошибки браузера
скрывают подробные журналы вызовов, которые могут содержать введённый текст.

Разрешены только HTTPS-запросы к исходному хосту в `/couriers/ru_RU/`, каждый
запрос проверяет наличие корпоративного VPN-маршрута. Проверка сертификата
включена, внешние переходы и WebSocket заблокированы. Скрипт нажимает только
подтверждённую кнопку входа; не меняет справочники и не запрашивает реестр.
Конечный результат — приватный `onec-browser-status.json`, в выводе только
признаки входа, HTTP-коды, необходимость 2FA/смены пароля и известные метки
навигации. Не сохраняет полный DOM, скриншоты или данные ответов 1С.
Успех этой проверки ещё не подтверждает полноту и семантику списка курьеров.

HTTP 402 от `e1cib/login` не трактуется автоматически как неверный пароль:
сборщик сохраняет ответ приватно, а в выводе показывает только числовые
`reason` и фиксированные категории причины (реквизиты, лицензия, права,
блокировка, 2FA, срок пароля). Полные сообщения, пути и имена не выводятся.

Браузерный вход вводит символы клавиатурой, дожидаясь отложенного select()
в штатном focus-обработчике 1С, и отправляет Enter из поля пароля (этот путь
подтверждён в обработчике Oub). Перед отправкой и в capture-обработчике Enter
проверяется точное совпадение обоих полей с приватно сохранёнными значениями.
В диагностике только признаки совпадения; при усечении/изменении полей вход
не отправляется. Это проверка автоматизации ввода, а не доказательство
верности сохранённых реквизитов и не обход серверной аутентификации.

При успешном ручном входе в чистом сеансе и отказе автоматического входа
`onec_route_check.py` сравнивает Mac и VPS без реквизитов: версию и SHA-256
начальной страницы/загрузчика, HTTP-коды и форму начального authSettings.
POST additionalAuthSettings с пустым телом подтверждён штатным загрузчиком
до ввода пользователя. Не печатает challenge, cookies, URL справки или
содержимое ответов. На Mac запускается отдельно с включённым корпоративным
VPN; на VPS — `probe_powerbi_vpn.py --address 10.210.254.19 --onec-route-check`.
Это диагностика различий маршрутов, а не утверждение причины отказа.

`check_onec_on_mac.sh` — локальная проверка ручного входа после
совпадения статических ответов Mac и VPS. Работает только на macOS с уже
установленным Google Chrome и корпоративным VPN. Устанавливает библиотеку
Playwright в отдельный пользовательский venv и открывает временный профиль
существующего Chrome. Логин и пароль вводятся только в самом окне 1С,
не запрашиваются в Терминале и не сохраняются скриптом на Mac.
Локальный режим не перехватывает запросы, не подменяет DNS и не блокирует
WebSocket или service worker. Ожидание ручного входа до трёх минут продолжает
обработку событий Playwright; блокирующий input() не используется.
Серверный режим по-прежнему проверяет tun-маршрут перед каждым запросом.


После Enter форма скрывается до завершения запросов 1С. Серверная проверка
теперь ожидает не скрытие окна само по себе, а конечный успешный ответ входа
с обработкой событий браузера (до 45 секунд). Первоначальный HTTP 402 до
появления формы не считается отказом введённых реквизитов. При успешном
конечном входе промежуточные отказы не выводятся как ошибка учётной записи.
Регрессионный тест в Chromium моделирует уже скрытую форму и задержанный
конечный ответ: браузер остаётся открытым до получения ответа.

`check_onec_on_mac.sh --compare-vps` сравнивает успешный ручной ввод с уже
сохранёнными реквизитами на VPS. Через существующий SSH/Happ маршрут читает
приватный JSON в память Mac, без вывода/сохранения его содержимого. SSH сам
запрашивает пароль VPS через терминал. Перед Enter/кнопкой входа в исходной
форме 1С сравниваются значения полей; в вывод попадают только
`username_matches_vps` и `password_matches_vps`. Реквизиты VPS не меняются.
Контекст сравнения и временные диагностические файлы уничтожаются при выходе.

`check_onec_on_mac.sh --sync-vps` переносит именно реквизиты успешного ручного
входа в приватный файл VPS. Флаг явно включает захват полей собственной формы
перед отправкой; значения остаются только в памяти. При отказе входа или
отсутствии захваченного ввода VPS не меняется. После подтверждения входа
и закрытия браузера SSH запрашивает пароль VPS; JSON передаётся только через
stdin SSH, не через аргументы или историю команд. На VPS файл атомарно
заменяется с правами 600 и сразу запускается серверная проверка входа.
Пароль не печатается и не сохраняется на Mac. Прямой список курьеров этот
шаг ещё не получает и публичную вторую метрику не изменяет.

После подтверждения серверного входа запустите
`probe_powerbi_vpn.py --address 10.210.254.19 --onec-login --onec-inspect-ui`
через `onec-venv/bin/python`. Сборщик ждёт появления основного интерфейса
и сохраняет приватный `onec-interface.zip` (права 600) в
`/opt/courier-analytics/private`: снимок окна и подписи видимых кнопок/заголовков.
Архив может содержать внутренние данные интерфейса; в публичный репозиторий
он не попадает. Значения полей, cookies, токены, сетевые ответы и хранилища
браузера не экспортируются. Разделы не открываются, записи не изменяются.
При неудаче снимка команда возвращает ошибку даже при успешной авторизации.

`--onec-inspect-roster` вместо `--onec-inspect-ui` перед снимком открывает
только точные пункты «Самозанятые» → «Курьеры». Если пункт отсутствует или
неоднозначен, навигация останавливается; архив содержит текущий экран и
`navigation_stopped_at`. Сбор подписей учитывает нестандартные элементы 1С.
Архив может содержать персональные данные видимой части списка, поэтому
остаётся приватным; в публичные агрегаты его содержимое не переносится.
Кнопки создания, изменения, записи и удаления не нажимаются. Это осмотр
интерфейса, а не полная выгрузка: пагинация и фильтры ещё не подтверждены.
Перед каждым переходом ожидается появление видимого пункта до 20 секунд:
основная оболочка 1С появляется раньше меню. Вложенная подпись одного пункта
не считается вторым пунктом; разные видимые совпадения останавливают переход.

Подтверждённый пользователем отбор базы ДС 7745: «Номер точки» = 7745;

исключены «Мобильный автокурьер» и «Мобильный велокурьер»;
«Тип занятости» включён, «Не равно» 1 (тестировщики).
Тип 3 означает аутсорс, тип 5 — самозанятых; условие != 1 нельзя заменять
списком [3,5] без отдельного подтверждения. Служба и ограничение заказов
не являются дополнительными условиями отбора. Эти правила пока не применяются
сборщиком автоматически: сначала требуется привязать и проверить поля формы.
Снимок формы содержит идентификаторы, типы и координаты видимых полей,
состояния checkbox, без значений текстовых полей. Список без подтверждённых
фильтров и проверки полноты не является базой для публичной метрики.

После успешного открытия списка `--onec-inspect-roster` вводит 7745 в
подтверждённое поле `form0_НомерТочки_i0`, завершает ввод Tab и проверяет,
что значение сохранилось. Изменяется только отбор списка, не карточки курьеров.
Архив дополнен значениями строго разрешённых полей отбора и структурой
элементов настроек/таблицы для проверки checkbox и полного исключающего списка.
Данные пароля и поисковой строки не собираются. Наличие 7745 в поле само
по себе ещё не подтверждает фильтрацию/полноту: `filters_verified` и
`complete_roster` остаются false; публикация базы по этому снимку запрещена.

Ввод номера точки выполняется клавиатурой (выделение, очистка, посимвольный
ввод, Enter и Tab): программный fill может не обновить внутренний буфер 1С.
После ввода собирается структура таблицы без значений ячеек и раскрывается
подтверждённая кнопка «+1» списка исключённых типов для их проверки.

Осмотр также собирает приватный кандидат базы из таблицы: только ID, ФИО,
доступ и тип занятости. Навигация Control+Home, PageDown и Control+End
ограничена 60 страницами/90 секундами; повторы ID удаляются, изменение одной
записи во время прохода вызывает ошибку. Неожиданные колонки, выключенный
доступ и тип занятости 1 отвергаются. Телефоны/ИНН в кандидат не экспортируются.
Неподвижность экрана не доказывает полноту: `complete_roster` остаётся false,
фиксируются страницы, причина остановки и новые ID при переходе в конец.
Для следующей проверки открывается только известная команда «Вывести список»
в меню «Еще»; диалог не подтверждается, структура сохраняется в архиве.
Ни кандидат, ни видимый экран автоматически не публикуются в дашборде.

При подтверждённых фильтрах штатный вывод списка теперь настраивается
на колонку Id: «Снять все» → только Id; «Only selected» обязательно выключен.

Проверенный штатный экспорт списка 1С подключается к текущему показателю №2

Новая база имеет приоритет над пятидневной активной базой только для 7745

Обновлённые сборщик и publisher запускаются из dashboard-code, с прежними
refresh.lock/publish.lock и proxy.env. Временный корпоративный VPN направляет
только 10.210.254.19/32 и закрывается после запроса; прочие VPN-задачи не
прерываются. Новая служба получает отдельный onec-roster.lock. Неудачная

### Закрытый сайт с авторизацией

`bash tools/enable_private_dashboard.sh` на VPS устанавливает отдельную
HTTPS-версию `https://courier-7745.147.90.10.158.sslip.io` (адрес выбран пользователем).
Это серверная авторизация, не JavaScript-проверка: страницы, скрипты и JSON
закрыты до входа. Старый GitHub Pages сохраняет только публичные агрегаты.
Персональные данные в репозиторий или публичные feeds добавлять нельзя.

Установка создаёт системного пользователя courier-web, отдельный venv
`/opt/courier-dashboard/venv` (Flask/Gunicorn), копию интерфейса в
`/opt/courier-dashboard/site`, службу `courier-web.service` на 127.0.0.1:8099.
Caddy автоматически получает HTTPS-сертификат; в существующий Caddyfile
добавляется import отдельного site-файла. Если 80/443 заняты другим сервером,
установка останавливается, не отключая его. При активном UFW открываются
только необходимые 80/tcp и 443/tcp. Данные двух агрегированных feeds
копируются root-службой раз в минуту; у веб-приложения нет доступа к
учётным данным сборщиков и приватным отчётам.

При первом запуске логин и пароль (минимум 12 символов) задаются в консоли,
пароль — скрытым вводом. `/etc/courier-dashboard/users.json` хранит scrypt-хеши,
settings.json — случайный ключ сессий; файлы root:courier-web 640, каталог 750.
База сессий и лимитов — `/var/lib/courier-dashboard` (courier-web, 700).
Cookie Secure/HttpOnly/SameSite=Lax; сессия на сервере действует 8 часов,
отзывается при выходе, смене пароля или удалении пользователя. POST входа
и выхода защищены CSRF. После пяти неверных попыток с IP — ограничение
на 15 минут. Секреты не передаются в аргументах команд и не публикуются.

Для нового пользователя или замены пароля выполните на VPS от root:
`/opt/courier-dashboard/venv/bin/python /opt/courier-dashboard/app/app.py --add-user`.
Повторная установка обновляет интерфейс/службы, сохраняя существующие аккаунты
и ключ. Форма входа появляется только на новом закрытом адресе; защита этого
сайта не меняет доступность существующего GitHub Pages. Персональная
детализация потребует отдельного защищённого API и ещё не включена.

Медицинский feed берётся в первую очередь из опубликованного clone
`/opt/courier-analytics/publisher/data/medical-books.json`: медицинский сборщик
не обязан записывать его в current-site. Для обоих feeds предусмотрены
резервные публичные копии; перед копированием используются общие валидаторы
агрегатов с удалением неразрешённых полей. Отсутствие медицинского feed
сохраняет предыдущую копию или даёт пустой набор записей (недоступность,
не 0%), не блокируя установку. Отсутствие основного feed без сохранённой
копии останавливает запуск. Повторная установка не запрашивает сохранённый пароль.

### Персональная детализация автоматических метрик

`bash tools/enable_private_details.sh` получает свежую базу 1С с колонками
Id и Name (текстовая выгрузка всех отфильтрованных строк), затем под прежними
refresh.lock/publish.lock обновляет слоты и публичные агрегаты, обновляет
закрытый сайт и копирует персональные снимки. Пароли остаются сохранёнными.
Выход из 1С и временного VPN выполняется штатным сборщиком.

ФИО сохраняются только в приватных наблюдениях/roster-cache и
`/opt/courier-analytics/private/details/YYYY-MM-DD-SHOP.json` (600).
`courier_details.py` группирует записи по ID, хранит ФИО, слоты, плановое и
фактическое время, статус и длительность опоздания; телефоны и ИНН исключены.
Набор 1С применяется только в пределах актуальности текущего дня.
Старые даты без сохранённой персональной выгрузки не восстанавливаются
предположениями. ФИО, не переданное источником, явно отмечается.

Синхронизатор раз в минуту копирует эти снимки в
`/opt/courier-dashboard/details` (root:courier-web, 2750; файлы 640).
Доступ возможен только через авторизованный `/api/details/SHOP/DATE/METRIC`;
статический доступ к деталям отсутствует. Закрытая копия HTML включает
private-details.js, публичный Pages — нет. В окне расчёта появляются поиск
по ФИО/ID, группы и таблицы; фиксируются время персонального снимка и
согласованность групп с числителем/знаменателем. При разных снимках или
неполных фактах выводится явное предупреждение. Ночные завершения выбираются
тем же completion_reporting.choose, что и агрегат. Для ЛМК пока показывается
сообщение об отсутствии персонального источника. Ручные метрики не меняются.

Публикация по-прежнему использует валидаторы публичного feed с разрешёнными
полями: персональные снимки, имена и ID не передаются в GitHub.

При потере предпосылок расчёта за ту же дату `merge_feed` сохраняет последний
подтверждённый процент (кроме заполненности слотов, связанной с текущими
booked_places/capacity), добавляя `last_success_at` и `stale_reason`.
В ячейке появляется ⟳, в окне — время первоначального расчёта и причина
задержки. Это не новый актуальный расчёт. Повторные ошибки не обновляют
время сохранённого результата; новая корректная выгрузка снимает отметку.
С другой даты значение не переносится, корректный 0% заменяет старое значение.

`bash tools/restore_private_metrics.sh` восстанавливает доступные последние
проверенные расчёты ДС 7745 за 03.11.2026 из recovery-манифеста (только
анонимные числа и время публикации), обновляет закрытый интерфейс и
показывает журнал службы 1С для диагностики первопричины. №7 не заполняется
догадками: подтверждённого результата за эту дату не было.

Автосбор перед каждым чтением восстанавливает включение фильтров 4/5/7
(доступ, тип курьера, занятость) и выключает дополнительные 6/8 (лимит заказов,
служба). Значения и исключения по-прежнему проверяются строго. Это устраняет
зависимость от сохранённой в 1С галочки «Тип курьера». При закрытии списка
chips используется щелчок по заголовку, затем состояния проверяются повторно.
В журнале `roster_check` выводятся только признаки проверок, причина отказа
экспорта/верификации и количество — без ФИО, ID, паролей и содержимого документа.

Тайм-ауты осмотра теперь записывают точный `stage` (включая номер фильтра,
видимость, щелчок и ожидание состояния). Сбор сначала ждёт видимого тела
списка. Если после успешного входа операция зависла, новый диагностический
ZIP заменяет старый даже при невозможности сделать screenshot; в нём
отмечаются `failure_stage`, время, текущие фильтры и наличие изображения.
Парольная форма, значения произвольных полей и текст исключения браузера
не сохраняются. `bash tools/check_onec_refresh.sh` запускает проверку и
печатает статус; при успехе обновляет метрики и закрытую копию данных.

Закрытие popup исключённых типов выполняется через Escape: модальное окно
1С может блокировать щелчок по captionbarTitle. После Escape обязательные
галочки проверяются заново, поэтому закрытие popup не ослабляет проверку
отбора. Регрессионный браузерный тест проверяет недоступный для щелчка
заголовок и закрытие popup клавиатурой.

`diagnose_missing_plan.py --date YYYY-MM-DD --shop 7745` выполняет только
чтение: проверяет подлинный план 23:59, получает текущие слоты выбранного ДС,
сопоставляет точные ключи (тип, слот, ID курьера), находит другие текущие
записи того же курьера и читает известные endpoints истории бронирования
лимитированных слотов и расписания курьеров. Для сохранившегося слота
проверяется также сырой ответ, включая записи, отфильтрованные как cancelled.
Нет новых неизвестных endpoints, изменений плана, публикации или записи
статусов. Результат `private/missing-plan-DATE-SHOP.json` (600) содержит
персональные сведения и предназначен для приватной сверки; токены, пароли,
cookies и заголовки авторизации не экспортируются. В консоли только числа
пропавших записей и путь. Ошибка чтения источника не считается невыходом.

Диагностика также читает общий `/v1/schedules/slots/ID/history?slot_type=manual`
(или limited) и `/v1/schedules/slots/dates/history?date=DATE&shopno=SHOP` —
оба маршрута подтверждены клиентскими функциями MP/LP исходного сайта.
Это важно для полностью удалённых ручных слотов, которых уже нет в текущем
списке. Времена версий date_start/date_end не подменяют фактическое начало
и конец работы shift_start/shift_end: история удаления сама по себе не
подтверждает выход или невыход курьера.

### Подтверждённое отключение курьера

`exclude_disabled_courier.py --date DATE --shop SHOP --courier ID` создаёт
приватное исключение с основанием `user_confirmed_disabled` и временем
подтверждения, затем пересчитывает выбранную дату и публикует агрегаты.
ID не зашивается в исходный код/публичный JSON: политика хранится только в
`private/metric-exclusions/DATE-SHOP.json` (600, каталог 700).

Применяются отдельные копии текущих записей, плана и актуальной базы;
исходный план 23:59 не меняется. Курьер исключается из всех расчётных
популяций этой ДС/даты, включая исторические ночные завершения. Вместимость
лимитированных слотов не меняется. Приватная детализация показывает количество
подтверждённых исключений. Другие даты и ДС не затрагиваются.

План, политика исключений, cache 1С и персональные снимки используют общий
state_dir также при историческом пересчёте. Устаревшая/неподходящая по дате
база 1С не заменяется пятидневной базой при наличии native-cache: сохраняется
последний подтверждённый результат с соответствующей отметкой.

#### Removed planned booking with an explicit current no-show

Frozen-plan attendance retains the original courier population. If a courier has
exactly one frozen booking and that booking is absent from the current slots,
`planned_facts.index` can use explicit same-day `Не вышел` facts from their
surviving bookings only when every surviving record agrees and none contains an
actual start or end. A cancellation by itself is insufficient. Arrivals in a
different slot, unknown statuses, contradictory facts, or multiple frozen
bookings remain unresolved. This does not modify source slots, the frozen plan,
slot-fill counts, or the separate metric-seven completion population. Private
attendance details retain the original planned times and identify the source
slot for the no-show evidence.

#### Separate public entry for networks unable to reach the dashboard VPS

`install_dashboard_edge.sh HOST NEW_PUBLIC_IPV4` runs **on a separate, clean
Ubuntu/Debian entry VPS**. First verify that its IP is reachable from the user's
actual fixed and mobile networks with Happ disabled, and point a DNS A record
for HOST at that IP. Remove conflicting AAAA records unless working IPv6 is
configured. Allow inbound TCP 80/443 in the hosting firewall. Choose a server
whose outbound HTTPS route to the current origin works as well.

The installer preserves the origin, its collectors and its account store. Caddy
terminates browser HTTPS and proxies over certificate-verified HTTPS to the
existing authenticated app. It rewrites the upstream Host to the app's existing
allowlisted hostname. It does not copy private files or passwords and does not
cache authenticated content. Relative login/logout/API URLs stay on the new
browser hostname; Secure host-only cookies bind there. The origin's no-store
and authentication responses pass through unchanged. Its current rate limiter
will see the edge IP, so failed-login limits are shared by users of this entry.

The installer refuses an occupied listener instead of changing an existing web
server, and validates origin authentication before configuring the proxy.
After certificate issuance, verify `/login` returns 200, `/api/session` and
`/data/dashboard.json` return 401 without a login, then test login, details and
logout in a browser **without Happ from both user networks**. A test from the
coding environment alone cannot establish user-network reachability. No DNS or
hosting account is supplied by this script; server provisioning and hostname
ownership must exist before installation. Keep the old address until these
checks pass. Remove the edge's individual site config and reload Caddy to
withdraw this additional entry; the origin remains available at its old URL.

#### Diagnose direct browser reachability before changing hosting

Run `tools/check_dashboard_access.py` on the user's Mac with Happ disabled. It
uses only Python's standard library, requests no credentials, changes no proxy
or DNS settings, and prints DNS, TCP 80/443, HTTP and certificate-verified HTTPS
checks. The fixed-IPv4 HTTPS check retains the original TLS SNI and Host, so it
separates DNS failure from transport/TLS failure. A successful probe in the coding
environment is not a substitute for this user-network check.

On the existing VPS, `bash tools/check_dashboard_server.sh` reports service
state, web listeners, local authentication responses, TLS validation, and web
firewall rules without changing them. Expect login 200 and unauthenticated
session/data 401. Compare these server results with the Mac output before
choosing a DNS, TLS, firewall, browser-proxy or routing repair. A browser timeout
on a bare IP alone does not establish IP blocking (HTTPS upgrading and host
routing can differ). No new hosting purchase is required for these diagnostics.

For a user-network trace where DNS and TCP succeed but application HTTP/TLS
requests time out, `bash tools/enable_dashboard_alternate_address.sh` adds
`https://courier-7745.147.90.10.158.nip.io/7745.html` on the existing VPS.
This tests hostname-dependent filtering without purchasing or moving hosting.
DNS must resolve to the current IPv4, local unauthenticated APIs must return
401, and staged Caddy configuration must validate before reload. The alias
proxies to the existing loopback app with its original allowlisted Host, so the
account store, authentication and private HTML remain unchanged. It preserves
the old hostname and does not change collectors or firewall rules. Check the
new hostname from the actual user networks with Happ disabled; successful DNS
or a response from a different network does not establish accessibility there.
If it still times out, compare a bare-IP HTTP request and local server checks
before concluding a hostname change can repair transport filtering.

#### Automatic retries and two-day reconciliation

Run `bash tools/enable_reliable_refresh.sh` on the existing VPS to install bounded
1C retries and the two-day collector. The hourly 1C service restarts after a
failure with a 120-second delay, capped at three starts in a 30-minute window.
The existing slot timer collects yesterday and today separately every 15
minutes using `refresh_recent_days.py`; this refreshes prior-day completion
facts without applying today's roster to a historical report. A failed date is
recorded privately and does not prevent attempting the other date. Current-day
collection failure returns nonzero, so systemd does not publish a failed run.
The normal refresh/publication locks and confirmed-value preservation still
apply. `/opt/courier-analytics/private/refresh-health.json` stores date-level
success/error classes without tokens or personal data.

A courier with one frozen booking can also be matched to an actual arrival in a
rebooked slot if all reported starts identify exactly one unambiguous same-day
shift and the source has an explicit arrived status. Midnight placeholders,
missing times, conflicting starts and multiple original bookings remain
unresolved. The original frozen slot/time/population are preserved; lateness
is measured from that original start, with provenance shown in private details.
Explicit no-show reconciliation remains available. No courier is silently
excluded for cancelling or moving a booking. These safeguards cannot invent
missing facts or guarantee source availability; retained values remain visibly
marked when a source cannot support a fresh result.

#### 1C grid-scan timeout after a successful login

The automatic collector takes a passive, nonempty sample of the current grid
rather than clicking and paging through it before export. The sample validates
required columns, active access and non-tester employment, but is never accepted
as a full roster. Completeness still requires the native all-filtered-row text
export (`OnlySelected=False`, unique Id/Name columns) and inclusion of every
sampled ID. The keyboard scanner remains available for separate diagnostics.

Verified data is saved before the optional diagnostic screenshot; a screenshot
failure records `screenshot_available=False`, omits the PNG and retains the JSON
archive. This prevents a rendering timeout from discarding verified source data.
Use `bash tools/check_onec_refresh.sh` after updating the code to recollect 1C,
then refresh recent-day metrics and synchronize the protected site. Existing
bounded automatic retries remain active; filter or export verification failures
still preserve the prior snapshot and keep its stale marker visible.

#### Restore saved 1C filter values, not just enablement

`onec_filters.restore_values` sets the confirmed filter values through native
controls after selecting point 7745: access Yes, employment Not
equal 1, courier type Not in list with exactly codes 6 and 9, and no top-level
service filter or saved list-search text. It changes list filtering only, never
courier records. Comparison dropdowns and reference autocomplete choices must be
exact and unambiguous. Incorrect type values are cleared through the evidenced
native clear control and reselected; the type field's own chip count is checked
as well as the expanded overflow values, preventing unrelated chips from
establishing the type filter.

The entire filter predicate is checked again before a grid sample or full
export. Invalid or unsupported UI selections fail closed with a stage-specific
private diagnostic, rather than timing out on an empty filtered grid or
publishing an incorrect roster. Both browser timeout and validation failures
retain a fresh diagnostic bundle. A wrong saved night-only `In list` selection
was the cause of the November 4 empty-grid failure; previous versions restored
checkboxes but left those values unchanged.

The point must be committed before value restoration: the blank-point initial
form can show only a scalar courier-type field, without comparison or list
controls. Reading its nonexistent comparison input would time out before point
selection. Checkbox enablement is restored first; selecting point 7745 then
materializes the comparison/list controls used by the confirmed filter workflow.

If the quick courier-type comparison does not exist even after selecting the
point, restore it through the user-confirmed **Ещё → Настроить список → Отбор**
route. The settings form ID and comparison editor are read from the current UI.
The collector requires exactly one native condition row containing both
`ТипКурьера` and its comparison, changes only that comparison to Not in list,
then applies Finish editing and restores the two mobile-type exclusions on the
main form. The available-fields tree alone cannot satisfy this condition.
Ambiguous/missing settings rows are never applied. Existing Filter-tab state
and an empty value list after changing comparison are supported. Private failure
snapshots include visible settings-grid structure for diagnosing UI differences.

Official route references: [Customizing lists](https://1c-dn.com/library/user_manual_customizing_lists/)
and [Filtering lists](https://1c-dn.com/library/user_manual_filtering_lists/).
Those pages document Configure list, the Filter tab, comparison selection and
Finish editing. Actual successful execution still requires verification on the
installed 1C configuration; local fixtures are not a live source verification.

The captured 1C menu uses NBSP in captions such as `Настроить список...`.
Open list settings with the evidenced `form0_popup_ФормаНастройкаСписка` ID when
available; caption fallback and comparison choices use whitespace-tolerant exact
matching. Normalize whitespace in known UI filter values and output-format
captions only. Credentials, courier IDs, names and native exported-row parsers
retain their existing strict handling. This prevents a visually identical menu
caption from timing out because of U+00A0 instead of ASCII space.

The captured live settings form also exposes the courier-type comparison on
**Main/Основные**, directly as a modal `…Элемент5ВидСравненияЭлементаОтбора_i0`
input with a matching `_DLB`. Prefer this evidenced control over navigating to
Filter: the live tab captions are outside `form1_container`. Derive the actual
input ID, require a unique visible match, verify its field label is
`ТипКурьера`, set Not in list through native selection, and apply the evidenced
`…_ФормаЗакончитьРедактирование` command. The compact-tree route remains a
fallback for other layouts. Main-form policy validation still gates the export.

The explicit `check_onec_refresh.sh` restarts the read-only roster service so an
in-flight automatic retry cannot return the previous imported code after a
repository update. Successful verification then refreshes recent-day metrics
and the protected data copy. It does not reset saved credentials or snapshots.

For native enum dropdowns, `_choice` waits for the selected value without
refocusing the input or pressing Tab. 1C's blur path can dispatch the editor's
previous buffer while the selection callback is pending. Applying settings is
performed only after the expected value is observed. Typed numeric/reference
entry retains its separate native commit flow. An asynchronous picker regression
covers cancellation of a pending choice by premature focus/Tab.

Native list export derives its form prefix from the single visible
`formN_UnckeckAll` control. It does not assume `form1`: opening list settings
earlier in the session can allocate another form number. Hidden old forms are
ignored, ambiguous or unrecognized dialogs are rejected before selecting
columns. The all-row, Id/Name-only and sampled-ID completeness checks remain in
place. The safe `roster_check.export_stage` status identifies the failing export
step without printing native error text or courier data.

#### Снятые смены в детализации явки

Если запись из фиксированного плана пропала, `plan_cancellations.collect`
читает известную историю бронирования соответствующего слота. Снятие
подтверждается только для того же ДС, даты, типа и номера слота, исходных часов
и ID курьера. Запись должна действовать на момент окончания съёмки плана и
иметь однозначное последующее время снятия. Отсутствие записи, ошибка API или
неоднозначная история сами по себе не подтверждают снятие.

В закрытой детализации №4 появляется группа «Снятые смены — история» с ФИО,
ID, исходным слотом, временем снятия по Москве и именем снявшего из источника.
Роль снявшего не угадывается. Исходный план и его знаменатель сохраняются:
снятие не равно отключению курьера и не подменяется статусом «Не вышел».
Подтверждённое снятие без факта работы больше не блокирует №4/№5; №5 по-прежнему
считает только фактически вышедших. При переносе подтверждённый выход имеет
приоритет, а история снятия остаётся видна отдельно. Конфликтующие факты
выхода остаются неразрешёнными. Персональная история хранится только в
приватных снимках и закрытой детализации, публичный feed содержит лишь агрегаты.

`update_private_frontend.sh` обновляет также `private-details.js`, когда
закрытая детализация уже включена; повторная установка сайта и учётных записей
для обновления колонок не требуется.

#### Автоматическое обучение (№9), ДС 7745

`bash tools/enable_training.sh 'HTTPS_GOOGLE_SHEETS_URL_WITH_GID'` включает сверку с вкладкой Google Sheets,
предоставленной пользователем, начиная с 05.11.2026. Ссылка передаётся только на
сервере и не зашивается в публичный код. Настройки хранятся на VPS
в `/etc/courier-analytics/training.json`, старые ручные даты сохраняются.
Новый показатель `training` передаётся в существующем анонимном feed,
персональная сверка — только через авторизованную детализацию №9.

Каждая строка считается фактом обучения по колонке «Отметка времени» (Москва).
«Знает/Не знает» не ограничивает расчёт. Для выбранной даты берётся проверенный
снимок активной базы 1С этой же даты: доступ Да, исключены мобильные типы и
тестировщики. Числитель — уникальные ID этой базы с записью об обучении не
позднее выбранного дня и текущего момента. Знаменатель — вся проверенная база.
Повторные строки сворачиваются до самого раннего обучения по ФИО.

В текущей таблице нет ID: используются только точные полные ФИО с нормализацией
регистра, пробелов и е/ё. Сокращения, опечатки и одинаковые ФИО у разных ID
не угадываются. В детализации доступны обученные, курьеры базы без
подтверждённого обучения и записи таблицы без однозначного совпадения в базе.
Последняя группа не входит в процент: в ней могут быть отключённые курьеры,
курьеры другой базы или имена, требующие исправления в таблице.

CSV читается сервером через стандартный HTTPS экспорт только указанной вкладки;
логины, cookies и права доступа Google не изменяются. Копия хранится приватно
в `private/training/latest.csv` (600). Проверяются заголовки, даты, полнота строк,
тип ответа, ограничение размера и тайм-аут. Ошибка источника/ФИО базы не даёт
ложный 0%: предыдущий подтверждённый результат этой даты сохраняется с отметкой
задержки. Остальные метрики обновляются независимо. Сверка запускается вместе
с обычным обновлением данных каждые 15 минут; отдельный таймер не нужен.

#### №7: доля доработавших среди фактически вышедших

По уточнению пользователя знаменатель №7 включает только уникальных курьеров
с подтверждённым статусом выхода (`on_time`, `early`, `late`). Неявка, снятая
запись и ожидание без фактического выхода не входят в знаменатель. Если у
курьера несколько учтённых смен, проверяются только смены, на которые он
вышел; все они должны закончиться не раньше допуска в 10 минут. При отсутствии
окончания фактически начатой смены показатель остаётся неподтверждённым.
Без вышедших — прочерк, не 0%. Правило отчётной даты ночных смен сохранено.

Новая база `slot_completion_arrived_by_actual_night_end_date` отделена от
старой `slot_completion_by_actual_night_end_date`; старый процент с другим
знаменателем не выдаётся за последнее подтверждение новой формулы.
Персональная разбивка и публичное окно расчёта используют тот же знаменатель.
Новые автоматические расчёты №7 имеют приоритет над прежней ручной историей.

После `git pull` команда `bash tools/enable_arrived_completion.sh` обновляет
интерфейс, пересчитывает текущие дни и запускает отдельную задачу
`courier-completion-recalculate` для истории ДС 7745. История берётся из API,
включая ночные смены; изменяется только №7 и его детализация. Соседние метрики
сохраняются. Задача работает под блокировками обновления/публикации, имеет лимит
30 минут и не зависит от SSH-сеанса. Прогресс:
`journalctl -u courier-completion-recalculate -n 20 --no-pager`.
Ошибки источника не превращаются в выдуманный процент; подтверждённые значения
новой формулы сохраняются с отметкой задержки.

Служба обновления ждёт `refresh.lock` до 180 секунд и `publish.lock` до 120
секунд, вместо мгновенного отказа при пересечении задач. Установщик №7
сохраняет это поведение в отдельном drop-in. Если текущий сбор всё же упал,
он выводит журнал и отдельно ставит исторический пересчёт в очередь. Уже
работающая историческая задача не запускается второй раз. Блокировки сохраняются.
