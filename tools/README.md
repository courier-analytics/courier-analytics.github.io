# Импорт выгрузки смен

`import_slots.py` читает лист «Смены» XLSX, создаваемого кнопкой
«Выгрузить слоты». Требуется Python 3 и `openpyxl`:

```sh
python3 -m pip install openpyxl
python3 tools/import_slots.py /путь/к/отчёту.xlsx
python3 -m unittest discover -s tests -v
```

Команда выводит только агрегаты. Исходные выгрузки, сессии и токены нельзя
класть в репозиторий или каталог публичного сайта. При вызове `read_export`
из Python результат содержит ID курьеров; он предназначен для защищённой
обработки на сервере, не для публикации.

Обработка:

- Одна строка XLSX — слот; список ID курьеров разбирается отдельно.
- Охват берётся из самого отчёта: учитываются и прямые слоты ДС,
  и включённые в выгрузку кластеры. Один `shopno` не заменяет этот охват.
- Групповым строкам не присваиваются общие статус и время смены:
  каждый курьер получает признак `api_required`.
- Пустое окончание смены означает неизвестное значение, а не завершение
  или невыход. Классификация посещаемости пока не реализована.
- Заполненность мест = сумма «Записалось» / сумма вместимости.
  Уникальные курьеры считаются отдельно; одинаковый человек в двух слотах
  занимает два места. При нулевой вместимости процент равен `null`.
- Повторные слоты и несовпадение количества ID с записавшимися приводят
  к ошибке вместо публикации неполных итогов.

Проверенный образец за 25.10.2026: ДС 5818, 42 лимитированных слота,
102 места, 57 записей курьер–слот, 56 уникальных курьеров, 14 групповых
слотов. 48 записей требуют индивидуальной детализации из API.
Это 55,88% занятых мест. Скриншот показывал 56/102: снимки ещё нужно
сопоставить по времени и логике подсчёта; не подменять 57 мест 56 людьми.

## Дополнение через API

`enrich_slots.py` получает детали по каждому дню, типу слотов и каждой
области выгрузки: прямой ДС и всем указанным кластерам. Читает существующий
файл сессии; токен передаётся curl через stdin, не через аргументы процесса.
Проверка TLS включена. Запросы только GET, изменение слотов не выполняется.

```sh
python3 tools/enrich_slots.py /защищённый/путь/report.xlsx \
  --session /root/curator-session.json \
  --proxy socks5h://127.0.0.1:18080 \
  --output /opt/courier-analytics/data/enriched-summary.json
```

Объединение идёт по дате, типу, ID слота, ID курьера и области запроса.
Повторные ID отклоняются. Изменения состава записавшихся, вместимости,
времени и отсутствие слота дают диагностику и код выхода 2; предыдущий
отчёт остаётся нетронутым. Новые слоты из API не добавляются в старый Excel.
Индивидуальные статусы, время записи, начало и конец сохраняются отдельно
в памяти. На диск выводятся только агрегаты и диагностика, без имён,
телефонов и ID курьеров. Отсутствующие факты не восстанавливаются догадками.

`attendance_metrics_ready` пока всегда `false`: показатели выхода,
опозданий и завершения смены не публикуются до проверки правил и снимка
плана. XLSX не содержит время записи, необходимое для фиксации плана на
23:59; оно запрашивается в API. Историю плана нельзя восстановить полностью
из текущих записей, если записи уже удалены.

Реальное чтение XLSX и живое API-обогащение проверены на VPS: 57 записей,
14 групповых слотов, пять записей без времени окончания, расхождений нет.
Локальный SOCKS-прокси пока зависит от Mac/Happ/SSH-туннеля.

## Регулярное обновление и сайт

`build_dashboard_feed.py` публикует только дату, ДС, числитель, знаменатель,
процент и время отчёта. Пример для уже проверенного отчёта:

```sh
python3 tools/build_dashboard_feed.py /opt/courier-analytics/data/enriched-summary.json \
  --output /opt/courier-analytics/site/data/dashboard.json
```

Страницы читают `data/dashboard.json` при открытии, по кнопке и раз в минуту.
Новые даты добавляются к истории. Заполняется только строка заполнения слотов;
остальные новые метрики остаются `null`. При ошибке загрузки последнее
успешное состояние сохраняется. CSV отражает загруженную таблицу.
Наличие файла не подтверждает работу планировщика или свежесть API:
на странице показывается время исходного отчёта.

`refresh_dashboard.py` позволяет не загружать Excel вручную: читает API,
создаёт собственный защищённый XLSX на основе тех же полей, затем формирует
отчёт и публичный JSON. Это программный экспорт данных, а не нажатие кнопки
в браузере и не побайтовая копия файла сайта. При ошибке предыдущий
публичный файл не изменяется. Даты истории сохраняются.

```sh
python3 tools/refresh_dashboard.py --scopes tools/scopes.json \
  --feed /opt/courier-analytics/current-site/data/dashboard.json
```

В `scopes.json` пока только проверенный по XLSX охват ДС 5818. ДС 7745 не
добавлена: её кластеры ещё не установлены. Если меняется состав кластеров,
конфигурацию необходимо актуализировать; файл не обнаруживает их автоматически.
При расчёте нового дня снимок всех API-запросов не транзакционный:
изменения между запросами возможны. Новые XLSX хранятся в закрытом каталоге.

`deploy_dashboard_from_mac.sh` переносит версию в отдельный каталог VPS,
выполняет живое обновление и только после успеха меняет `current-app` и
`current-site`. На GitHub ничего не публикует. При обновлении сохраняет
предыдущую историю из текущего файла данных. Требуются работающие Happ,
SSH-туннель, файл сессии и Python venv на VPS.

Подготовлены `courier-refresh.service` и `.timer` с блокировкой `flock`.
Они обновляют текущий день каждые 15 минут; завершающий пересчёт предыдущего
дня отдельно ещё не реализован. Установка и включение таймера не выполнялись.
Пока прокси зависит от Mac, расписание нельзя называть автономным.
Статический GitHub Pages не видит файлы VPS: для публикации нужны отдельная
выкладка JSON в репозиторий либо перенос размещения сайта на VPS.

Установка из клона репозитория на VPS: `bash tools/install_on_vps.sh`.
Скрипт использует существующую сессию и SOCKS-прокси, проверяет живой запрос,
создаёт отдельный каталог сайта и только после успеха меняет ссылки
`current-app` / `current-site`. История активного JSON сохраняется.
Сам сайт GitHub Pages и расписание при этом не изменяются.
